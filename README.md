# vicky-skills

Claude Code skills for steering coding agents in any repository: star charts for planning, test-first builds, and reviews on three axes. They're built on ideas from [Matt Pocock's skills](https://github.com/mattpocock/skills), `ship-it`'s pictures come from Dex Horthy's [show-me](https://github.com/humanlayer/skills), `do`'s smallest-change rules from [ponytail](https://github.com/DietrichGebert/ponytail), `spark-joy`'s deep modules from Matt's improve-codebase-architecture, and `mission-brief` from Matt's to-spec and to-tickets, folded into one step. A star chart's black holes are the rabbit holes from Basecamp's [Shape Up](https://basecamp.com/shapeup), and its four boxes of knowns come from The School of Knowledge's "The Rumsfeld matrix explained". The viewscreen band is Tzafrir Rehan's [whats-agent-doing](https://github.com/tzafrir/whats-agent-doing), ported under its MIT License, which its files keep. The reader panel, the planning pages in your browser, `captains-log`'s high points and the ticket-drift agent come from two of Austin Marchese's videos, [The ONLY 4 Things You Need To Prompt Like An Anthropic Engineer](https://www.youtube.com/watch?v=_NzakzRXzLI) and [Nate Herk: The Most Valuable AI Skill to Learn In 2027](https://www.youtube.com/watch?v=42Y6z9KKRKc). The design moves in the review principles come from Jimmy on Software's [7 Mistakes That Cause Fragile Code](https://www.youtube.com/watch?v=wbW2dqjNC5w) and double-trouble.dev's [Negative Space Programming](https://double-trouble.dev/post/negativ-space-programming/). The main addition is approved examples: you approve the examples a build must pass before the agent writes any code.

They're also made for a backlog that grows faster than you can clear it. Agents are good at noticing what you forgot, like an edge case or a missed caller. When each of those finds becomes a ticket, every finished task leaves you more tickets than it started with. So these skills fold what an agent finds into the work you're already doing, and the never-a-V1 hook (from a tip by Austin on YouTube: never let the AI hand you a V1) holds them to it. Nothing becomes a ticket unless it truly has to wait.

No skill here shares a name with one of Matt's, so both plugins load without clashing. They describe two different workflows, though, so use one at a time.

| Skill | When it's used | What it does |
| --- | --- | --- |
| **`first-contact`** | When you type it | `/first-contact` sets a repository up for these skills, once: where its tickets, glossary and decision records are, and a `TESTING_STANDARDS.md` that says how testing is done there. Every testing skill reads that file first. |
| **`power-word-fix`** | When you type it | `/power-word-fix <what's broken>` sorts the problem, runs the skills that fit and ends on proof. |
| **`lay-course`** | When you type it | The lazy way in when you don't know where a session leads. You pick a council or an interrogation to work out what you want. It files a star chart of tickets, or a single ticket (a star) when the work fits in a session, and then stops or warps to it. Every star's spec is its approved examples. |
| **`mission-brief`** | When you ask to file tickets or issues, turn a plan into tickets, or convert tickets from another tool | After it checks the source material, the tracker and the codebase, it writes down what the conversation already settled as a spec, cuts it into slices with Given / When / Then examples, and you approve the examples on a page. Then it files a star chart, one star per slice. Tickets made by another tool get re-sliced the same way, never copied across. It asks you no new questions. An open one becomes an anomaly on the chart. |
| **`warp`** | When you say "warp" or "engage", or `lay-course` engages it | Clears a whole star chart in a single run: every star it can reach, or just the stars you name. It first files whatever those stars need that has no ticket yet. Then it opens the route in your browser: the charts, and a table with each ticket, its kind and what it needs from you. You trim it and answer its questions on that page, and it takes every answer up front and builds each star through to green CI in one pull request, without dropping out. What blocks it, it clears, works around or waits out. A star that waits on someone else stays open, and the landing report names it. |
| **`examples`** | Before a ticket is built, when a decision becomes a build, or when acceptance criteria are prose | Turns a ticket, rule or decision into Given / When / Then examples, opens them as a page in your browser, and writes the ones you approve as failing tests. |
| **`by-eye`** | When a build needs to see a page it changed, when `do` turns an example you see on a page green, or when you ask it to "look at it" | Looks at a page in a browser with no window, so nothing pops up on your screen: light, dark, a narrow screen and the keyboard alone. It boots the dev site under a memory cap and stops it after. The agent grades the page itself and keeps going, and leaves the screenshots in its scratch folder for you to look at later. It opens the windowed browser only when you have to sign in. |
| **`do`** | When you ask for a change or hand over a ticket or star chart | Builds behaviour-first from a request typed in chat, a ticket or a whole star chart: you approve Given / When / Then examples on a page in your browser, each becomes a red test, the code turns them green, and mutation proves the tests catch bugs. A case no example covers comes back to you as a new example. Small work needs no chart or ticket. |
| **`review`** | When you want a branch, pull request or work in progress reviewed | Reviews a branch on three axes at once: standards, spec and simplicity. Each axis is its own agent, and a diff under 40 lines gets one quick pass instead. They share one list of review principles: one point of entry, data read from its source, one copy of logic, and tests proved by mutation. |
| **`never-lupus`** | When something is broken, failing or slow | Finds the cause of a hard bug or a slowdown with a loop that goes red on it. |
| **`ship-it`** | When a pull request opens, a push changes it, or you ask for a description | Writes a pull request body, and rewrites it when a push changes what the pull request does. |
| **`machine-spirit`** | Before changing CI, and when a CI run is red, slow or stuck | Writes and debugs CI: workflows, path filters, runners, caches, required checks, and runs that are red, slow or stuck. |
| **`stacked-branches`** | When a follow-up is big enough or different enough for its own pull request, when you ask for a stack, or when a stacked branch is checked out | Builds and merges a stack of dependent pull requests with `gh stack` or `git-spice`. Small changes stay on the effort's one pull request, and each follow-up stacked on it is labelled `stacked`. |
| **`human-voice`** | When writing prose a person reads, and when text sounds like AI | Writes anything a person reads, in a register picked by the audience: eccentric and enthusiastic for a public showcase, plain for everything else. The agent drafts from guiderails, a list of moves to make, and never reads a list of AI habits to avoid. A lint script catches the habits a script can find and prints the move to make for each one. Every hit is rewritten before you see the draft. A draft over about 400 words also goes to a panel of readers from its audience, who list the questions it leaves them with. The agent answers what it can in the draft and shows you the rest. Its `reader_panel` setting picks `one agent` playing every seat, the default, or an `agent per seat`. |
| **`ui-design-101`** | When building or reviewing buttons, confirmations, deletes or per-row actions | Designs the actions in an interface for their hundredth use. |
| **`over-to-you`** | When a change needs a real client, a look, real hardware or an outside account to prove | Hands the checks only a person can do to you, as a short checklist on a page in your browser, with room for notes. It covers the whole branch, except what you've already passed on record, and stocks each check first: the props, state and scripts it needs are built fresh for that check, never borrowed from the world or left for you to build, and removed afterwards. You mark each item done, done with changes, failed or not tested, and there's room for extra tests and anything else. A long list comes in numbered sittings of seven, and nothing is dropped. |
| **`loose-lips`** | Before any commit, push or post, and when writing docs a stranger could read | Checks anything leaving the machine for an attack map and rewrites it by role. |
| **`robot-voice`** | When creating or editing a skill, agent file or prompt, or when an agent misreads one | Writes skills, agent files and prompts for maximum agentic ergonomics. |
| **`plot-twist`** | When you say "actually" or "instead", or reverse an earlier decision | Carries a change of direction into every ticket, pull request and doc that still says the old thing. |
| **`make-it-so`** | When you say "make it so" or "ship it", and when a `warp` or a star-chart build ends | Finishes a draft pull request: current with main, a QA checklist where a command or one read decides each item, a true body, marked ready, then CI watched until it's green. |
| **`gamma-shift`** | When you say "gamma shift" or ask what's waiting on you, or at session start when its setting asks | Works through the tickets waiting on you. Up to three whose wait is over get built per session, smallest first, onto one draft pull request for you to read, the rest are listed with what they still wait on, and your open decisions come back as one round of questions. Its `gamma_shift` setting picks what happens at session start: `off`, `remind` for a one-line count, or `engage` for a run in the background. |
| **`loose-ends`** | Before calling an effort done, after every push to an open pull request, and after a merge | Settles every ticket an effort touched and keeps the pull request body true. Before the effort is done, it runs `engrave` on each snag the effort hit. |
| **`marie-kondo`** | When an effort lands, on a first visit to a repo, or when you ask for a cleanup | Deletes merged branches and worktrees, plus your own branches on the remote whose work has landed, and keeps what sparks joy. Other people's branches stay. |
| **`spark-joy`** | When you say "spark joy" or "deepen", or every few days when its setting asks | Folds one shallow module in the busiest code into its caller, with the tests at its seam holding the behaviour, and opens a draft pull request. Its `deepen_every_days` setting runs it in the background at session start every that many days, and `0`, the default, never does. |
| **`red-pen`** | When writing meets an audience (players, customers, the public), or examples need your approval | Opens drafts on a page in your browser and writes back what you leave. Specs, tickets, pull request bodies and internal docs skip it. |
| **`drawing-board`** | Before a window or screen layout gets built or resized, or when you say "sketch it" | Draws the window at true scale inside your screen, as a draw.io sketch in your browser. You move and resize boxes, and it reads your changes back as numbers, like "pack cell 24 → 32", and flags a broken size rule. The approved sketch is saved where a `Sketches:` line in `docs/agents/` says, or beside the window's code. draw.io itself is fetched once, pinned to one release and checked by hash. |
| **`interactive-page`** | When a skill hands you a draft file or a checklist, or has a question with options for you | Shows the file as a page in your browser, with text to edit, boxes to tick, a comment box per draft and one at the end, and options to click for a question. Done writes your answers back into the file. With no browser, the file opens in your editor. |
| **`cerebro`** | When you ask whether, how or why an agent or skill does something, after `captains-log` and `review`, when a decision is recorded, and at the end of `make-it-so` and `sup` | Looks forwards. It answers a question about your agent setup, reads the follow-ups you've sent, forecasts what you'll ask next, and proposes the changes before you have to ask. It asks itself the questions you'd ask about each proposal, and the answers go into the proposal. |
| **`council-of-elrond`** | When you ask for a council, pick it in `lay-course`, or bring a design question with no answer yet | Puts your idea in front of a table of designers. A skeptic, a dwarf with an axe, an elf who looks far ahead, a ranger who walks it through, a rules keeper, an enthusiast and two troublemakers with new ideas argue it with you, whether it's a game rule, a character build or a piece of code. The chair and the rules keeper speak every round, and the rest take turns, so you hear every voice at least every other round. Each round ends on open points, each with a pick, and the council ends by picking the road: a star chart, one star, or a warp right now. Once it starts, every reply comes from the seats, answers to your questions included, and the seats can stay in character the whole way. Nothing opens in your browser and nothing turns into a round of bare questions until Frodo picks the road. After that, a page may open, but only to choose the next moves. The agent starts one when you ask for it, pick it in `lay-course`, or bring a design question you haven't answered yet. |
| **`fireside-chat`** | When a writing skill reaches its interview, or you say "interview me" | Interviews you for a post or article in your name, as the Bard, an old teller of tales at the fire who stays in character until the interview ends. It reads what shipped first, so it only asks what you alone know: the war story, the why, the credit. It gives a pick on choices like the angle or the picture, and none on the story, and it keeps your answers in your own words for the draft. |
| **`interrogation`** | When you say "grill me" or "interrogate me", or an anomaly needs your answers | Is the council's hard mode: it asks you questions only, the sharpest first, until nothing is left open, and writes your answers as examples. |
| **`true-names`** | When a term is fuzzy or disputed, or when editing the glossary or a decision record | Sharpens a project's terms in its glossary and records decisions as you make them. Each record holds one design-wide rule, in a short Brief and a short Rationale of at most 100 words together. One feature's reasons go in a comment at its code instead. |
| **`away-team`** | When a decision waits on a fact from docs, an API, source code or a spec | Answers a question from primary sources in a background agent and posts the findings on the ticket the question belongs to. |
| **`standing-orders`** | When you say "todo", "add to todo" or "for later", or work would otherwise be parked | Jots one short line in the repo's `.todo` without asking, and tells you it's there to work when you're ready. The line points at its star or ticket and goes when that closes. |
| **`summit`** | When a session starts, when you ask whether you're closing more than you open, and when `captains-log` or `cerebro` looks at the trend | Counts the tickets opened and closed since your last session and over 30 days, and grades the 30 days: A if you closed more than you opened, B if the two are within 10%, C if you opened more. The line shows in the viewscreen band. The session-start count comes from the springboard hook, so it needs `standing_orders` on, a `.todo` the repo ignores, and GitHub. |
| **`sup`** | When you ask "sup", "where are we" or for a status report, return after a break, or a long stretch of work ends | Catches you up in one screen: done, changed, lessons engraved, waiting on you, next. |
| **`familiar`** | When you type it | `/familiar` makes the session your familiar. It watches every other live session on the machine, writes each snag into a debt note per session, sends you a tip at the end of a stretch of work, and fixes or files each note when its session hands off. At each handoff it also reads the whole session against your first ask and the charter, since the watch alone misses about a third of what goes wrong. A repo turns it off with `Familiar: off` in its tracker doc, and `familiar_plugin_repo` names the checkout where fixes to this plugin get built. It speaks in the voice of the kind you pick in `familiar_kind`: the owl, quiet, unless you choose the imp, quasit, raven, parrot, pseudodragon, cat or spider. Every kind does the same work. |
| **`conn`** | When you type it | `/conn` writes the state into the tickets and pull requests first, then posts a thin handoff on the pull request or ticket, or as a note where your own agent instructions keep notes when there is no tracker: the goal, the links, and what this session was in the middle of. After you clear, type `/sup` and the new session finds it. |
| **`captains-log`** | When you type it | `/captains-log` looks backwards: it runs a retrospective on a session and finds what would make the next one go better. It also finds what went exceptionally well and marks the line behind it kept, so a later cleanup leaves that line alone. With the skill ledger on, it lists the skills nobody has started in 60 days, each with a pick: keep, merge or delete. Its follow-up trends and high points go to `cerebro`. |
| **`engrave`** | When you say "codify", "lesson", "for the future" or "from now on", when a snag cost a retry, and for each snag `loose-ends` or `captains-log` finds. Other corrections wait for `loose-ends` to hand them over in one batch | Turns one snag into a rule that stops it next time: a check or a hook where one fits, a skill line where neither does. It builds the rule this turn and ends with a `📓 Engraved:` line. The rule goes to the plugin's repo, your `CLAUDE.md` or the project repo, whichever owns it. |
| **`history-monks`** | When you ask for a rebase on main, and before pushing a branch main has moved past | Rebases a branch onto a main that moved: what landed owns the form, the branch keeps its behaviour, and the old patterns a merge hides get converted too. |
| **`sentinels`** | When `do`, `placebo` or a review asks for a mutation pass, or a mutation run dies | Mutation-tests changed code with the repo's tool, a tool pulled down for the run, or by hand, and keeps a run alive under a memory cap. |
| **`placebo`** | Whenever a test is written or reviewed; the audit runs only when you ask for it | Lists the kinds of test that look like proof and catch nothing, and the agent checks every test it writes or reviews against them. Ask it for an audit and it deletes, merges or rewrites them across a suite. |
| **`retcon`** | When you say "undo", "revert" or "put it back" | Undoes exactly what you name, and leaves every other change alone. |
| **`nwn-model-tooling`** | When working on Neverwinter Nights models, HAK files or headless Blender scripts | Points to the Blender with Neverblender, `cleanmodels` and the neverwinter.nim tools, and how to call each. Its plugin settings name your Blender commands and the folder of unpacked stock resources. |
| **`video-captions`** | When a task links a video or asks what one says | Reads a video through its captions. |
| **`codex-image-gen`** | When a task says "use codex" for an image, or a `codex exec` call looks stuck | Makes or edits an image through the Codex CLI's image tool. |
| **`is-this-a-meme`** | When you type it | `/is-this-a-meme <thing>` explains it, then lands it with a meme. The `dungeon-master` style memes on its own, and nothing else does. |

The `dungeon-master` output style is relaxed, focused and exact: the answer first, the next action last, a register per topic, and memes when an idea needs to land. Pick it with `/output-style vicky-skills:dungeon-master`.

## Hooks

Each hook is tagged. A **(recommended)** hook only refuses, asks or warns, so it keeps an agent out of trouble and never starts work of its own. An **(experimental)** hook starts work by itself: it runs a skill or an agent in the background, writes to your repo, or tidies your branches. Read what one does before you turn it on.

Turn a hook on or off under `/plugin`, in the plugin's settings. The last column names the setting and says whether it starts on or off. Most hooks need `jq`, and the git guards need `git`.

| Hook | What it does | Setting |
| --- | --- | --- |
| **Gamma shift** (experimental) | The experimental backlog-clearing powerhouse. Use it with care: at `engage` it works with no one watching. At session start it builds one batch: up to three tickets whose wait is over, smallest first, in one background agent. Say "gamma shift" for the next batch. It also runs `spark-joy` every `deepen_every_days` days and the `ticket-drift` agent every `drift_every_days` days (7 by default). The builds and the spark-joy run all land on one shared `gamma-shift-<date>` branch with one draft pull request, apart from the branch you work on, and the drift check comments on tickets. At `remind` it only says how many tickets wait on you. Its ticket builds and drift check need the tracker file `/first-contact` writes. A repo turns the drift check off with `Ticket drift: off` in its `docs/agents/issue-tracker.md`. | Off (`gamma_shift`: `off`, `remind` or `engage`) |
| **Auto-tidy** (experimental) | Prunes origin's branches at session start, and asks the agent to run `marie-kondo` when a local branch's upstream is gone, as it is after a merge in the browser. When your clone stands on a branch whose pull request merged, it hands the clone back to main, or moves commits made after the merge to a fresh branch. Uncommitted changes keep the clone where it is. A branch with an open pull request stays too, and the session works in a worktree. | Off (`auto_tidy`) |
| **Springboard** (experimental) | Keeps a marked block in a repo's `.todo` with at most five things only you can do, each with its link: a draft page to finish, a green pull request to merge, a pull request that waits on you. It rebuilds the block at session start and after a push, a merge or a page that opens, and leaves your own lines alone. A session opens on the first item, the tickets opened and closed since your last session, and the 30-day summit verdict. It tells an agent to shorten a `.todo` line past one sentence of 80 characters. It only touches a repo whose `.gitignore` ignores `.todo`, and needs `gh`. | On (`standing_orders`) |
| **Lesson hint** (experimental) | Adds a line of context when your message teaches a lesson, such as "codify that" or "for the future", so the agent runs `engrave` and builds a rule before it replies. `plugins/vicky-skills/scripts/lesson-hint.sh` has the phrase list. | Off (`lesson_hint`) |
| **Decision-record hint** (recommended) | Reminds an agent writing a decision record that a record holds a broad architecture rule, and the reason for one class, item or value goes in a comment at its code. | On (`adr_scope_hint`) |
| **After push** (recommended) | After a `git push`, reminds the agent to reread the pull request body and settle its work items. In a `warp` run, it keeps the agent building every target on the draft and finishing it with `make-it-so`. | Always on |
| **One pull request per effort** (recommended) | Keeps each session's work on one pull request, opened once, so CI runs once. A second one goes through only stacked on it with the `stacked` label, when the one below changes at least `guard_pr_stack_min_lines` lines (300) or the new body says why it's separate. A stack holds at most `guard_pr_stack_limit` (3). A forge command that only appears as quoted text, such as a `sed` pattern or an `echo`, is not counted, unless the text goes to a shell, `eval`, `ssh` or `xargs` to run. That check needs `gawk`, and without it quoted text counts. A refusal that moves the work says to delete the branch it leaves behind. It also refuses a pull request, issue or comment whose text credits an AI. Credit in a commit is the git hook's job. In a repo `first-contact` set up, it refuses a pull request body without `ship-it`'s Status, Summary, Proof and Risk sections, and a body filled from the commits with `--fill`. It also holds a body back until the session has run `human-voice`, the plain-prose pass `ship-it` asks for. A `PR template: off` line in `docs/agents/issue-tracker.md` turns that check off. | On (`guard_pr`) |
| **Plane blocks need a hard reason** (recommended) | Refuses `plane block` unless the command ends with `# hard: <reason>`. Plane's API can add a blocked-by link but not remove one, so a softer order goes in a `Waits on:` line. | Off (`guard_plane_block`) |
| **`tea` stdin** (recommended) | Refuses a `tea` call without `</dev/null`, which can hang until it times out. Needs `gawk`. | On (`guard_tea_stdin`) |
| **Check the gate first** (recommended) | Refuses a `🚪 Waiting on you:` message that names a pull request already merged or closed, looked up with `gh` or `tea`. A lookup that fails or takes over three seconds lets it through. | Off (`guard_gate_state`) |
| **No local paths** (recommended) | Refuses a commit that adds a home folder, a Nix store path or your username. `local_path_exempt_repos` lists repos it skips, and a line marked `local-path-ok` passes. | On (`guard_local_paths`) |
| **Worktrees in one place** (recommended) | Refuses `git worktree add` anywhere but the repo's `.claude/worktrees/` folder, and keeps it out of `git status`. After a `git merge`, it removes the merged branch's worktree and branch once every commit has landed. A repo that has a `Drop worktree: <script path>` line in `docs/agents/testing.md` has that script named and run for the removal, in place of `git worktree remove`. | Off (`guard_worktree_place`) |
| **No pushing behind main** (recommended) | Refuses a push from a branch that main has moved past. | On (`guard_push_behind`) |
| **Git branches, pushes and commits** (recommended) | Refuses a new branch made on top of a branch that hasn't merged, a push to main or master (and `--all` or `--mirror`), a commit message that credits an AI, and a commit that sets its own author or committer. A new branch from `origin/main` goes through, and so does a stack made with `gh stack` or git-spice. A trunk repo, one whose `AGENTS.md`, `CLAUDE.md` or `docs/agents/` says `Trunk: on`, or that `git_guard_trunk_repos` names, takes the push to main and refuses the new branch instead. | On (`guard_git`) |
| **No commits on a merged branch** (recommended) | Refuses a commit or push on a branch whose remote branch is gone, and gives the command for a fresh branch from main with the commits to carry over. | On (`guard_merged_branch`) |
| **No skipped do steps** (recommended) | Refuses to mark a `do` or `warp` pull request ready when a step never ran and the body gives no `Skipped: <step>, because` reason. It also refuses a `do` pull request whose body has no `Plan check:` line or no `Examples:` line, and any pull request that changes the Given, When or Then wording of an approved test without your tick on a page. When `do`, `over-to-you` or `make-it-so` starts, it reminds the agent of each step's proof and the red-pen draft file. When `do` starts, it asks for the plan check, which argues against the plan before the first test. When a council starts, it keeps every line in the seats until Frodo speaks. When `review` starts, it asks whether each finding you fix should be made impossible next time. | Off (`step_guard`) |
| **Tickets only through mission-brief** (recommended) | Refuses `plane file`, `tea issues create` and `gh issue create` until the session has started `mission-brief`, which checks the source material, the tracker and the codebase before it writes a ticket. | On (`guard_ticket_filing`) |
| **Mutation passes start with sentinels** (recommended) | Refuses a mutation-testing command, such as Stryker, a `mutate.sh`, mutmut, cargo-mutants or PIT, until the session has started `sentinels`. That skill keeps the pass to the lines you changed and the tests that reach them, so it doesn't run for half an hour. A tool named inside quotes, like in a commit message, doesn't count. | On (`guard_sentinels_first`) |
| **A suggested next goes in `.todo`** (recommended) | Sends back a reply that names what comes next, such as a `Next:` line, "my pick for next" or "still want...?", until `standing-orders` has jotted it in `.todo` that turn. It also refuses any write to `.todo` that doesn't go through `standing-orders`' `todo.sh`. It stays quiet where `.todo` isn't gitignored or `docs/agents` says `Todo file: off`. | On (`guard_todo_next`) |
| **A refused key is checked before it is blamed** (recommended) | After a git or ssh command fails with the ssh client's `<host>: Permission denied (publickey)` line, tells the agent to compare your keys with the forge's and read the forge's status page before it asks you to add a key. A forge having an outage turns away keys it already holds. | On (`guard_publickey_hint`) |
| **A refused call is not repeated unchanged** (recommended) | Refuses a tool call identical to the one just before it, when a hook refused that one. The agent has to act on the refusal first: change the call, run the step it names, or wait. A call with another step in between goes through. | On (`guard_same_refusal`) |
| **A rebase conflict goes through history-monks** (recommended) | When a `git rebase` stops on a conflict and `history-monks` hasn't started, tells the agent to abort and rebase again under it. A conflict settled by hand keeps only the branch side. | On (`guard_rebase_monks_hint`) |
| **Only you make a repository public** (recommended) | Refuses making a repository public, through `gh repo edit` or `create`, `gh api` or `tea`, unless your last message says "public". That can't be taken back once someone has seen it, so it's never an agent's own pick. | On (`guard_publish`) |
| **No browser windows for local pages** (recommended) | Refuses the windowed Playwright browser for a page on this machine, so a `by-eye` check uses the headless server and no window opens on your desktop. A sign-in page on a real host still opens. | On (`guard_windowed_browser`) |

## Install

The plugin needs Claude Code 2.1.271 or later. In a Claude Code session:

```
/plugin marketplace add vickydotbat/vicky-skills
/plugin install vicky-skills@vicky-skills
```

To offer it to everyone who works in a repository, run this once from that repository and commit the `.claude/settings.json` it writes:

```bash
claude plugin marketplace add vickydotbat/vicky-skills --scope project
```

Turn on auto-update under `/plugin`, then **Marketplaces**. The plugin has no version number, so every commit to `main` is an update.

## The charter

`skills/CHARTER.md` says what the whole workflow is for, in eight lines: you get what you meant, done is proven, facts come from their source, and so on. Every skill ends with a `Charter:` line naming the lines it serves, and a test fails when one doesn't. The `familiar` ties each snag it logs to the line the snag broke. A snag that breaks no line means the charter is missing one, so the familiar drafts it for you.

## Approved examples

An example says what the game or app does, in its own words, with no code in it:

> Given a creature charmed by another, when its charmer hits it, then the charm ends.

The agent drafts examples, but only the ones you approve become tests, and each test must fail before the code exists. The full rules for a good example are in the `examples` skill.

The hook only sees edits made through Claude Code's own edit tools. Back it in each repository with a merge gate: a code-owner rule that names you for files ending `ApprovedExamples`, or a CI check that refuses a change to one without your approval.

The idea is example-guided development, Daniel Terhorst-North and Matt Wynne's name for what behaviour-driven development, acceptance test-driven development and specification by example share. TDD is one part of it. Dave Farley's [The Industry Is Catching Up](https://www.youtube.com/watch?v=EkH_uoybj8k) is the best short case for it.

`examples`' check for entries no test would miss, its split for a star with more than six rules, and `do`'s predicted runs come from Marco Emrich's [EXACT Coding](https://github.com/marcoemrich/EXACT-Coding), shown in Emily Bache's [interview on Modern Software Engineering](https://www.youtube.com/watch?v=a6HYpocKwXU).

## Development

```bash
claude plugin validate .
tests/run-all.sh
```

Run both before every push. CI runs every test once a pull request is marked ready, and refuses a draft.

The skills' eval cases live in `plugins/vicky-skills/evals/`, and you run them by hand with the scripts in `tests/evals/`. Each run starts a real Claude session on your own credential, so CI never runs them. One run of the mission-brief case cost $0.22, and each script caps every run at $3. `tests/eval-coverage.sh plugins/vicky-skills` names each skill that has no case yet, and starts no model.
