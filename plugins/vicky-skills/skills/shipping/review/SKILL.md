# Review

> _You shall not pass, until standards, spec and simplicity all agree._

Three-axis review of the diff between `HEAD` and a fixed point:

- **Standards**: does the code follow the repo's written rules and the house principles in [PRINCIPLES.md](PRINCIPLES.md)?
- **Spec**: does every approved example pass, within the decisions on record, and which prose asks still lack an example?
- **Simplicity**: what can be deleted?
- **Cause**, when the branch claims to fix something: does it fix the cause or a symptom, and is there a better way? The questions are in [CAUSE.md](CAUSE.md).

The tracker is named in `docs/agents/issue-tracker.md`. If that file is missing, tell the user to run `/first-contact`.

Read the repo's testing standards first, where the `Testing standards:` line in `docs/agents/testing.md` names them (`TESTING_STANDARDS.md` at the root when the line is absent): they win over this skill's defaults.

## Steps

1. **Pin the checkout and the fixed point.** The work under review may sit in a worktree, not the clone the session started in. For the checkout, use the path or branch the user named, or the build's own worktree when `do`, `warp` or `gamma-shift` calls this skill. Otherwise take the current checkout (`git rev-parse --show-toplevel`) when its branch differs from the base and holds commits or changes of its own. When none of these settles it, list `git worktree list` with each one's branch, and the open pull requests (`gh pr list`, or `tea pr list </dev/null`), and ask the user which one to review and what they want reviewed. Run every later git command and file read in that checkout. For the fixed point, use what the user named. When `do`, `warp` or `gamma-shift` calls this skill, the fixed point is the merge-base with the pull request's base branch (`git merge-base HEAD origin/<base>`): never ask. Otherwise, if the user named nothing, ask. Run `git rev-parse <fixed-point>` and confirm `git diff <fixed-point>...HEAD` is non-empty. Done when you hold one checkout path, the ref resolves and the diff has content. When it does not, say which check failed and stop.
2. **Find the spec.** A ticket key in a commit or the branch name, a path the user passed, or ask. Called from `do`, `warp` or `gamma-shift`, take the build's ticket, or "none" for a chat request, and never ask. Done when you hold a ticket key or the user's "none".
3. **Size the diff** with `git diff --shortstat <fixed-point>...HEAD`. A **small diff** has fewer than 40 lines inserted and deleted together. The count holds every changed line, tests and comments included: "the production change is small" is no exception, and `pr-guard` refuses a pull request body or comment line that starts `Skipped:` and names review. Done when you know which branch step 5 takes.
4. **Gather the outside law.** A **law file** carries the repo's rules that a reviewer's tools cannot reach. Read the repo's `AGENTS.md`, `docs/agents/` and its `Testing standards:` line. When any of them names standards, decisions or principles kept outside the repo (a wiki page, a tracker page, any project memory reached through an MCP server or a login), read each named page whole this session, plus every outside page that governs the changed area. Write them verbatim into one file in your scratch folder, each page under a heading with its title and its version or edit date, its own headings kept, in the form the repo's agent file gives a law file when it gives one: a reviewer quotes the line a finding breaks, and a summary has no line to quote. Then run `test -s <file> && realpath <file>` and use the path it prints, never one typed from memory: a session id remembered from an earlier session names a folder that holds no such file. `review-brief-guard` refuses a reviewer brief that names a missing file. A repo whose standards, decisions and principles all sit in its own files skips this step and writes no law file. Done when the printed path holds every named page, or you can say the repo names no rules outside it.
5. **Review it.**
   - **Small diff, unless the user asked for a full review**: review it yourself, with no subagent. Read the diff once per axis. For Standards, read the rules the repo's `AGENTS.md` names for the touched files, and the law file. For Spec, read the ticket's approved examples, and its prose only for asks no example covers. With no ticket, the user's ask is the spec. For Simplicity, ask what could be cut. Check every claim the diff makes about the repo, such as a file, a command or a setting, against the repo.
   - **Otherwise, dispatch the three reviewers in one message**, in parallel: `standards-reviewer`, `spec-reviewer` and `simplicity-reviewer` from this plugin. A repo that ships its own agent of the same name uses its own. Give each the checkout path, the fixed point and the law file's printed path. Give `spec-reviewer` the ticket key: with no ticket, give it the user's ask, in their words, as the spec.

   - **Cause**, when a commit, the ticket or the pull request body says the change fixes something: answer [CAUSE.md](CAUSE.md) yourself, in the main thread. No reviewer agent runs it, since it needs the problem the fix names. When the repo's `docs/agents/issue-tracker.md` says `Review cause: off`, skip it and leave the Cause section out of the report.

   When a reviewer's report leaves out a file in `git diff --name-only <fixed-point>...HEAD`, send it back to that reviewer with the missing files named, or read them yourself for that axis. A reviewer that answers `LAW MISSING` gets the law file written or its path fixed, and is sent again. Done when every axis has a result that covers every changed file and read the law file.
6. **Report** under `## Standards`, `## Spec` and `## Simplicity`, each verbatim or lightly cleaned, and `## Cause` when the branch claims to fix something, or else the line `Cause: no fix claimed`. Under `Review cause: off`, the report holds neither, and no Cause closing line. Keep the axes apart: a change can pass one and fail another. End with one line per axis, Cause included when it ran: its finding count and its worst finding. Then add the Laws line: run `bash ${CLAUDE_PLUGIN_ROOT}/scripts/law-lint.sh prove <fixed-point>` and paste the `Laws:` line it prints, which names each law the diff reaches, the proof it ran and the result, or reads `Laws: none touched`. It runs only the proofs the diff reaches. A failed proof, and an unproven law the branch added, are findings. Under `Law proofs: off` it prints that, and the report carries no Laws line. A finding on an approved-spec test goes to the user as a question, through `examples`' "Changing an approved example": never fix it in place, whatever its size. Then run `cerebro` as a forecast on the findings. Inside an effort (`do` or `warp` started this session, or the user asked for a build and a review), the report is not the end: fix each finding that waits on no one in the same turn, a big refactor included, and never as a question with a pick, then report again. Each review finding you fix, from a person or from a review agent, also gets a prevention verdict: when that kind of mistake can be made impossible, engrave it as the cheapest check, hook or standard line that holds it; otherwise write one line saying why not. Done when every section, its closing line, the Laws line and cerebro's proposals are in the reply, inside an effort every finding that waits on no one is fixed, and each fixed finding has its prevention verdict.
